# Сравнительный анализ методов тестирования

Анализ подготовил Боцман Алексей Андреевич (Т9-ИП-25-2) на примере
проекта «Обработка матрицы с XML-интеграцией».

## 1. Методы «чёрного ящика»

### Эквивалентное разбиение (основной метод варианта 4)

Входная область делится на классы, внутри которых программа ведёт себя
одинаково. Из каждого класса берётся один представитель.

Применение в проекте: я выделил допустимые классы матриц (1×1, 1×N, N×1,
N×M, числовые строки) и недопустимые (пустая, рваная, нечисловая,
неконечные значения), классы XML-сообщений, тайм-аутов и состояний
модулей конвейера. Именно класс «неконечные числа» выявил BR-01, а класс
«повторный запрос после сбоя» — BR-02.

### Анализ граничных значений

Проверяются значения на границах классов и рядом с ними.

Применение: матрица 1×1, одна строка, один столбец, размер 0 и 1 при
вводе, `timeout = 0`, заголовок `rows = 0` и `rows = -1`, значение
`1e309` (переполнение в бесконечность).

### Причинно-следственные связи (таблицы решений)

Комбинации входных условий (причин) связываются с реакциями (следствиями).

Применение: в конвейере причины «обработчик доступен», «форматтер
доступен», «данные корректны», «был предыдущий запрос»; следствия —
результат, `ModuleUnavailableError`, `InvalidDataError`, очистка каталога
обмена.

## 2. Методы «белого ящика»

### Покрытие решений

Каждое решение (`if`, `while`) принимает значения «истина» и «ложь».
Например, в `swap_extreme_rows` проверены случаи, когда минимум
и максимум находятся в разных строках, в одной строке и в последней строке.

### Покрытие условий

Каждое элементарное условие составного выражения принимает оба значения.
Для `not isinstance(row, list) or len(row) != columns` отдельно проверены
строка-кортеж и строка другой длины.

### Комбинаторное покрытие условий

Проверяются все комбинации элементарных условий. Для пары
`processor is None` / `formatter is None` проверены все четыре
комбинации: (нет, есть), (есть, нет), (нет, нет) и (есть, есть).

## 3. Сравнение

| Метод | Достоинства | Ограничения | Когда применять |
|---|---|---|---|
| Эквивалентное разбиение | мало тестов при широком охвате; не требует знания кода; хорошо находит контрактные ошибки | качество зависит от правильного выделения классов; пропускает ошибки на границах | первым этапом для любых входных данных и контрактов модулей |
| Граничные значения | находит ошибки «на единицу» и переполнения | без разбиения неясно, где границы; растёт число тестов | вместе с разбиением для размеров, индексов, тайм-аутов |
| Причинно-следственные связи | систематически проверяет комбинации условий; документирует бизнес-правила | таблица быстро разрастается при многих причинах | для логики с несколькими взаимосвязанными условиями (конвейер, режимы) |
| Покрытие решений | измеримо инструментами (`coverage --branch`); показывает непроверенные ветви | не проверяет отдельные условия внутри составных выражений | как минимальный критерий полноты набора в CI |
| Покрытие условий | проверяет каждое элементарное условие | не гарантирует покрытия всех ветвей | для составных условий с `and`/`or` |
| Комбинаторное покрытие условий | самый строгий критерий для составных условий | экспоненциальный рост числа тестов (2ⁿ) | для критичных условий с 2–3 операндами |

## 4. Рекомендации

1. Начинать с эквивалентного разбиения: оно дешёвое и даёт основу набора.
2. Дополнять его граничными значениями для каждого числового класса.
3. Для логики с несколькими условиями строить таблицу решений.
4. Покрытие решений использовать как контрольный показатель в CI
   (порог `--fail-under`), но не как цель: в проекте оба дефекта были
   в коде с 100 % покрытием.
5. Комбинаторное покрытие применять выборочно — только для коротких
   и критичных условий.
